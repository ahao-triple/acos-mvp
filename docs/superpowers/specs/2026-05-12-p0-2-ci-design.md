# P0/2 加最小 CI：在 GitHub Actions 上跑 typecheck + 两个 test 套件

> 对应 `CHANGES-BEFORE-AGENTS.md` 的 P0/2。
> 目标：让 `mini-pack` 的 typecheck 与两个 vitest 套件成为每次 push / PR 的强制 gate，而不是只能靠开发者本地自觉。

## 背景

P0/1 落地后，仓库进入 pnpm workspaces 模式：根目录 `pnpm install` 一次装好三处 workspace。`mini-pack/tests/integration/repo-build.test.ts` 已经会在测试里真实跑 douyin / kuaishou / vivo 三平台 build（spawn 时自带占位 env），是仓库最强的回归 gate。

仓库远端在 GitHub（`github.com:ahao-triple/acos-mvp`），自然走 GitHub Actions。

`pnpm verify` 的末段 `pnpm build games/gonglian-fangxian`（默认 douyin 平台）依赖 `DOUYIN_APPID` 环境变量；CI 上没有 `.env` 文件，跑到末段必失败。而 `test:pack` 的 `repo-build.test.ts` 已经把三平台 build 都覆盖了，是更强的 gate——所以 CI **不跑 `pnpm verify`**，直接跑 `test:game` + `test:pack` + typecheck。

## 决策

新增**单一** workflow `.github/workflows/ci.yml`，**单一 job**，串行执行最小步骤集：

1. checkout
2. setup pnpm 10
3. setup node 20，开启 `cache: pnpm`（setup-node 内置 lockfile-based pnpm-store 缓存）
4. `pnpm install`（workspaces 全装好；等价于 `pnpm bootstrap`）
5. `pnpm --dir mini-pack typecheck`
6. `pnpm test:game`
7. `pnpm test:pack`（含 `repo-build.test.ts` 三平台真实 build）

承担的代价 / 明确不做的事：

- 不跑 `pnpm verify`，原因如上
- 不拆 jobs / 不并行——MVP 阶段单 job 串行最简单；后续 P1/4 拆 `verify` 与 `verify:full` 时再决定 CI 是否要 build matrix
- 不预先 `pnpm approve-builds`——pnpm 10 默认对若干包（`@vivo-minigame/cli-server`、`core-js`、`esbuild` 等）跳过 install scripts。P0/1 验证里三平台 build 在这种状态下都过了，CI 先沿用同样行为，如果将来某个 build 因此挂掉再单独处理
- 不加自定义 `.pnpm-store` 缓存路径——setup-node 的 `cache: pnpm` 自带 lockfile-based 缓存，已经够用
- 不部署、不上传 artifacts、不发 release

## 文件改动清单

### 新增

**`.github/workflows/ci.yml`**

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - run: pnpm --dir mini-pack typecheck

      - run: pnpm test:game

      - run: pnpm test:pack
```

要点：

- pnpm 版本写 `10`，与本机一致；不能用 `9`（会与 pnpm 10 生成的 lockfile 格式冲突）
- `pnpm install --frozen-lockfile` 强制按 lockfile 装，任何依赖漂移都会让 CI 红——这是想要的行为
- job 名 `verify` 是历史习惯命名，与本地 `pnpm verify` 不是同一组命令；选这个名字是为了 GitHub UI 上看着像"verify"。如果觉得名字让人误会，未来重命名为 `ci` 或 `test` 都可以
- 没有自定义 env、没有 secrets——CI 完全靠 `repo-build.test.ts` 自带的占位 env

### 不动

- `package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`
- `CHANGES-BEFORE-AGENTS.md` 在落地后单独 commit 打勾，不在本次 spec 范围里讲怎么改
- 任何 `mini-pack/`、`games/*/`、`scripts/` 下的文件

## 已知风险与缓解

**风险 1：CI 环境与本机 macOS / Node 版本差异**

本机 Node 22 + macOS，CI Ubuntu + Node 20。`mini-pack/tests/integration/repo-build.test.ts` 在 worktree 验证过工作，但 CI 上首次跑可能暴露：esbuild 拉错 native binary、vivo CLI bin 在 Linux 上路径不同、tsx loader 行为差异等。

**缓解**：CI 首次运行作为 spec 验证步骤；如果首次失败，根据日志定位（通常是某个 install script 或 native bin 问题），可以**单独**加一个 follow-up commit 处理，不影响本 spec 的整体方向。

**风险 2：pnpm 10 的 ignored build scripts 列在 CI 上会变成 error 而不是 warning**

P0/1 验证里本机看到的是 warning（pnpm install 退出 0），但 pnpm 10 在某些 CI 环境会把 ignored build scripts 升级为 error。

**缓解**：spec 不预先 `pnpm approve-builds`；如果首次 CI 跑出 error，按需要选 (a) 在 workflow 加 `pnpm approve-builds --all` 步骤（最简单）或 (b) 在 `package.json` 加 `pnpm.onlyBuiltDependencies` allow-list（最精确）。这个决定留到那时再做。

**风险 3：第一个 PR 触发 CI 时，仓库可能没有 .github/workflows 解析权限的默认设置**

GitHub 仓库 settings → Actions → Workflow permissions 可能限制了 actions 不能写。这个 CI 工作流不需要写权限（只读 + 测试），但首次推送会触发 GitHub 提示。

**缓解**：仓库 owner（你）首次合并后到 settings → Actions 确认 workflow 已启用。

## 验证步骤

按顺序执行：

1. 本地把 `.github/workflows/ci.yml` 加进去，commit 推到一个临时分支（如 `feat/ci`）
2. 在该分支开 PR，观察 GitHub Actions：必须跑绿，全部 4 步通过
3. 在该 PR 上故意推一个会让 `mini-pack/tests/integration/repo-build.test.ts` 失败的改动（例如把某个 expect 改坏），观察 CI 必须红
4. 还原破坏后，CI 重新绿
5. merge 这个 PR 到 main，后续每个 PR 都会自动触发 CI

## 范围之外

- 把 `pnpm verify` 改成 CI 友好（拆 verify / verify:full）——这是 P1/4 的范围
- 给 difference-hunt 也跑 vitest（root `test:game` 当前只跑 gonglian-fangxian）——是独立缺陷
- build matrix（douyin × kuaishou × vivo 各跑一次 build）——是 P1/4 的 `verify:full` 范围
- 上传 build artifacts、发版自动化、部署——不是 P0 范围
- ESLint / Prettier / Biome 跑 CI lint——是 P2/6 决定后才能做

## 完成定义

- `.github/workflows/ci.yml` 存在并通过 GitHub Actions 首次绿
- 故意打破测试能让 CI 红
- `CHANGES-BEFORE-AGENTS.md` 里 P0/2 的复选框打勾
