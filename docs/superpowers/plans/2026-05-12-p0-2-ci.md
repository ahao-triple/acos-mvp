# P0/2 加 GitHub Actions CI — 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 给 acos-mvp 加最小 CI：每次 push 到 main 与每个 PR 自动跑 `mini-pack` typecheck + `test:game` + `test:pack`（含 `repo-build.test.ts` 三平台真实 build）。

**Architecture:** 新增单一 GitHub Actions workflow `.github/workflows/ci.yml`，单 job 串行：checkout → pnpm 10 → node 20（lockfile-based cache）→ `pnpm install --frozen-lockfile` → typecheck → test:game → test:pack。不跑 `pnpm verify`（末段 douyin build 缺 env 必失败；`test:pack` 已覆盖三平台 build）。

**Tech Stack:** GitHub Actions、pnpm 10、Node 20、actions/checkout@v4、pnpm/action-setup@v4、actions/setup-node@v4。

**Spec:** `docs/superpowers/specs/2026-05-12-p0-2-ci-design.md`

## Task 1: 在 worktree 内加 .github/workflows/ci.yml

**Files:**
- Create: `.github/workflows/ci.yml`

- [ ] **Step 1: 确认工作目录存在 .github 目录**

Run:
```bash
ls -la .github/workflows/ 2>/dev/null || echo "需要创建"
```

Expected: 输出 `需要创建`（仓库目前没有 `.github/` 目录）。如果已经存在 `.github/workflows/` 但没有 `ci.yml`，直接进 Step 2；如果存在 `ci.yml`，停下报告——可能是别人加过、需要先讨论冲突。

- [ ] **Step 2: 创建目录并写 ci.yml**

Run:
```bash
mkdir -p .github/workflows
```

然后 Write `.github/workflows/ci.yml`，**严格**按以下内容：

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v4
        with:
          version: 10

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - run: pnpm --dir mini-pack typecheck

      - run: pnpm test:game

      - run: pnpm test:pack
```

**关键约束：**
- pnpm 版本写 `10` 不是 `9`（清单原文写的 9，但仓库 lockfile 已经是 pnpm 10 格式）
- `pnpm install --frozen-lockfile` 必须带 `--frozen-lockfile`，让任何依赖漂移都让 CI 红
- 步骤之间是单 job 串行（任一失败立即停），不是 jobs 拆分
- `cache: pnpm` 是 setup-node v4 内置功能，会按根 `pnpm-lock.yaml` 做缓存键

- [ ] **Step 3: 本地 yaml 语法校验**

Run:
```bash
node -e "
const fs = require('fs');
const text = fs.readFileSync('.github/workflows/ci.yml', 'utf8');
console.log('lines:', text.split('\n').length);
if (!text.includes('actions/checkout@v4')) throw new Error('missing checkout');
if (!text.includes('pnpm/action-setup@v4')) throw new Error('missing pnpm setup');
if (!text.includes('actions/setup-node@v4')) throw new Error('missing node setup');
if (!text.includes('--frozen-lockfile')) throw new Error('missing frozen-lockfile flag');
if (!text.includes('pnpm test:pack')) throw new Error('missing test:pack');
if (!text.includes('pnpm test:game')) throw new Error('missing test:game');
if (!text.includes('mini-pack typecheck')) throw new Error('missing typecheck');
console.log('ci.yml structure OK');
"
```

Expected: 输出 `lines: 22` 左右、`ci.yml structure OK`。任一 throw 出现说明 yaml 内容写错了，回 Step 2 修。

> 注：这里**不**用 actionlint 或 yamllint 做严格 schema 校验——会需要额外依赖。结构性 grep 已足够。Yaml 真正的语法/语义错误只能等 GitHub 那边解析时暴露，本 plan 在 Task 3 验证步骤里覆盖。

- [ ] **Step 4: 看 git status，确认只有这一个新文件**

Run:
```bash
git status
```

Expected:
```
未跟踪的文件:
```

不应有任何其它改动。如果有，先核对。

- [ ] **Step 5: stage 并 commit**

Run:

```bash
git add .github/workflows/ci.yml
git status
```

## Task 3: 推送到 GitHub 触发实际 CI（合并后由 controller 与用户共同决定）

> 注：本 task 不在 implementer 范围；它需要影响远端共享状态（push），由 controller 在 review 通过后与用户对齐再执行。implementer 完成 Task 1/2 后即可 STOP 并报告。

**Files:**
- 无文件改动；仅 git 远端操作

- [ ] **Step 1（controller 执行）: 与用户对齐推送策略**

可选：直接 push main、push feature 分支开 PR、或本地先 merge 后稍后再推。`CHANGES-BEFORE-AGENTS.md` 的 P0/2 标注 `Verify` 部分原文要求"推一个故意打破 `test:pack` 的 commit，CI 应该红"——这需要先把 ci.yml 推上去才能验证。

- [ ] **Step 2（controller 执行）: 推送后观察首次 CI 运行**

push 后到 GitHub 仓库的 Actions 页面观察 `CI` workflow：
- pnpm install 是否成功（特别注意 ignored build scripts 是否升级为 error，spec 风险 2）
- typecheck / test:game / test:pack 全绿
- 总耗时大致在 2-5 分钟（首次没 cache 会慢一点）

如果失败：按 spec 风险 1/2 的缓解策略处理（pnpm approve-builds 等）；可能需要 follow-up commit。

- [ ] **Step 3（controller 执行）: 验证 CI 能"红"**

为了证明 CI 是有效 gate，在临时分支推一个故意打破测试的 commit（例如把 `repo-build.test.ts` 某个 expect 改坏），开 PR 观察 CI 是否失败。验证完立即 revert/丢弃这个分支，不合并到 main。

> 这一步是 spec `Verify` 步骤 3 的要求；可以放到合并后某个空闲时段做，不阻塞 P0/2 标记完成。
